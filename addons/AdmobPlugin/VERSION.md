## What the patches change

### 0001 — UMP privacy options + debug geography (M9-01; 3 files, +73 / −2)

1. `ConsentConfiguration.java` — `debug_geography` accepts any `java.lang.Number`
   (Godot passes GDScript ints as `Long`; v6.0 only accepted `Integer` and
   silently ignored the value — upstream issue #120, still open; fixed in
   upstream v7.0, which targets Godot 4.7).
2. `AdmobPlugin.java` — three UMP 3.x calls exposed to Godot:
   `can_request_ads()` → `ConsentInformation.canRequestAds()`,
   `get_privacy_options_requirement_status()` →
   `ConsentInformation.getPrivacyOptionsRequirementStatus()` (`"REQUIRED"` /
   `"NOT_REQUIRED"` / `"UNKNOWN"`), `show_privacy_options_form()` →
   `UserMessagingPlatform.showPrivacyOptionsForm()` + new signal
   `privacy_options_form_dismissed(Dictionary)`. Not present upstream in v6.0,
   v7.0 or `main` (checked 2026-09-22).
3. `Admob.gd` (GDScript facade template) — the same three methods plus
   `has_privacy_options_api()` (true only when the native plugin registered the
   new signal, i.e. the patched AAR is installed) and the forwarded signal.

No other class, resource, dependency or version changed (the rebuild differs
from the unpatched build only in `AdmobPlugin*.class` — line numbers shift in
the anonymous inner classes — and `ConsentConfiguration.class`).

### 0002 — RequestConfiguration value conversion (TASK/041; 2 Java files, +93 / −21)

4. `AdmobConfiguration.java` — reads what Godot 4.6 actually sends instead of the
   v6.0 casts: ints (`tag_for_child_directed_treatment`, `tag_for_under_age_of_consent`,
   `personalization_state`) as any `java.lang.Number` → `intValue()` (was `(int)` =
   `checkcast Integer`, fails on `Long`); `test_device_ids` as `Object[]`, keeping only
   non-empty `String` entries (was `(String[])`, fails on `Object[]`); `is_real`,
   `first_party_id_enabled`, `max_ad_content_rating` type-checked. An unreadable value
   is logged (`Invalid request configuration value '<key>' …`, type only, never the
   value) and its builder setter is skipped — the SDK keeps its current value; a
   missing / non-bool `is_real` is treated as real (no test devices). The VALUES and
   the setters called are unchanged (rating G, TFCD / TFUA unspecified = -1,
   personalization DEFAULT, test devices only when `is_real` is false).
5. `AdmobPlugin.java` `set_request_configuration()` — a `RuntimeException` is caught
   and logged (`request configuration NOT applied`) instead of vanishing in Godot's JNI
   bridge, and after `MobileAds.setRequestConfiguration()` the SDK's current
   configuration is read back and logged once:
   `set_request_configuration(): applied max_ad_content_rating=… tag_for_child_directed_treatment=…
   tag_for_under_age_of_consent=… personalization_state=… test_device_ids=<count> sdk_initialized=…`.

No other class, GDScript file, dependency or version changed: 0002 adds no API, no
TFAT / age treatment (GMA 24.9.0 has none) and does not touch `Admob.gd`. The
rebuild differs from the M9-01 AARs only in `AdmobConfiguration.class`,
`AdmobPlugin.class` and `AdmobPlugin$*.class` (javap: bytecode identical, line
numbers only). Two independent clean builds (existing and fresh upstream clone) were
byte-identical before install; `install` and `verify` reproduced the same bytes.

## RequestConfiguration defect (TASK/040 finding) — fixed by 0002 (TASK/041)

TASK/040 (Samsung A36, 2026-09-25) found that the M9-01 AARs (`e3ac9a6b…` / `90d35992…`)
never applied `RequestConfiguration`: Godot 4.6 passes the facade's dictionary ints as
`java.lang.Long` and arrays as `Object[]`, while v6.0 `AdmobConfiguration` read them with
`(int)` / `(String[])` casts, so `createRequestConfiguration()` threw
`ClassCastException` (swallowed by Godot without a log line) and
`MobileAds.setRequestConfiguration()` was never reached — max ad content rating **G**,
TFCD / TFUA and test device ids were NOT in effect. Upstream v7.0 / `main` (4b4ddce,
2026-05-27) fixed only the `Long` casts (`((Long) x).intValue()`); `(String[])` is still
there. `0002` fixes both for the GMA 24.9.0 production path;
`tools/release/release_readiness.gd` pins the corrected release AAR
(`PATCHED_RELEASE_AAR_SHA256`) and keeps the old SHA in `KNOWN_PLUGIN_DEFECTS`
(CODE if that AAR ever returns).

## Rebuild / verify

`tools/admob_plugin/README.md`. In short, from the repo root:

```
tools/admob_plugin/build_patched_plugin.sh baseline   # unpatched v6.0 == upstream release AARs
tools/admob_plugin/build_patched_plugin.sh build      # v6.0 + 0001 + 0002 into build/, installs nothing
tools/admob_plugin/build_patched_plugin.sh verify     # committed files == v6.0 + 0001 + 0002
```

Why v6.0 and not v7.0 (2026-05-27): v7.0 is built against **Godot 4.7 beta1**
(`godot.properties`: `godotVersion=4.7`, `godotReleaseType=beta1`) and the
maintainer states in issue #122 that "v7.0 requires Godot 4.7+ … for Godot 4.6.x
use v6.0". This project is pinned to Godot **4.6.3** (CLAUDE.md). v7.0 also does
NOT expose the three privacy-options calls — only the #120 fix.

Google SDK 24.x support window (developers.google.com/admob/android/deprecation,
read 2026-09-21): *Supported*; deprecation 2027-06-30, sunset 2028-06-30.
